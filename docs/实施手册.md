## 执行中任务补充 / 纠错

当存在非终态任务，或最近 2 小时内刚完成的任务时，直接在钉钉发送字段关系、表关系、业务规则等说明性内容，PersonZit 会将其识别为 `supplement`，而不是普通聊天。

处理链路：

```text
received -> authorized
-> intent:task-context-precheck 或 intent:zhipu
-> action:supplement
-> ack:dingtalk-stream
-> task description + EventLog 持久化
-> REVISE_TASK 队列
-> Codex/Claude 带补充规则重跑相关子任务
-> verification
-> 钉钉主动通知
```

规则：

- 若任务仍在执行，不强行杀掉当前 Agent；当前轮结束后进入修订执行，避免半途中断产生不确定状态。
- 若任务已处于验收阶段且尚未完成，先执行修订再允许完成。
- 若任务最近 2 小时内刚完成，可通过自然语言补充或显式指令重新打开并修订。
- 若云端意图模型超时或输出非法 JSON，使用当前任务上下文做本地兜底，不再降级为普通聊天。
- 显式命令：`补充 <任务ID> <补充/纠错内容>`。

# PersonZit 实施手册

> 适用版本：v0.1.0 ｜ 适用平台：Windows 10/11 + PowerShell
> 目标：按照本手册从零开始，一步步完成 PersonZit 的部署、启动、验证和日常使用。

PersonZit 是运行在 Windows 本地的 AI 工程任务编排 MVP：

- **Node.js CLI**（`bin/personzit.js`）：统一操作入口

## 4. 启动、停止与状态检查

### 启动服务（后台方式，推荐）

```powershell
node bin/personzit.js start
```

输出 `API 与 Worker 已启动`。此命令会：

- 后台启动 API 服务（`app.main`），日志按日期写入 `logs\api-YYYYMMDD.log`
- 后台启动 Worker（`app.worker`），日志按日期写入 `logs\worker-YYYYMMDD.log`，Agent 子进程不会额外弹出窗口
- 在 `runtime\` 写入 PID 文件用于 stop/status 管理

> `--foreground` 只让 API 输出在当前终端；Worker 仍会以后台服务方式运行。执行 `personzit stop` 可统一停止 API 与 Worker。

### 服务重启后的孤儿 Job 恢复

Worker 启动后会读取仍在 `RUNNING` 的队列 Job，并解析锁中的旧 Worker PID：

- 旧 PID 已不存在：Job 立即重置为 `QUEUED`，对应运行中的 AgentRun 标记为 `INTERRUPTED`，子任务回到 `PENDING`，由当前 Worker 重新领取；
- 旧 PID 仍是本机 Python 进程：不碰该 Job，避免影响仍活跃的 Worker；
- 无 PID 或无法判断：保留给既有 `stale_after_seconds` 心跳超时机制处理。

因此正常执行 `personzit restart` 后，不会出现任务卡在死 Worker 锁上约 30 分钟的情况。`stop` 在 Windows 上会按进程树终止 Worker 及其 Agent 子进程。

### 查看日志

日志默认写入 `%USERPROFILE%\.personzit\logs`，可在 `config.yaml` 中通过 `logging.directory` 指定目录：

```yaml
logging:
  directory: logs
  level: INFO
  retention_days: 30
```

常用命令：

```powershell
personzit status
personzit logs --service api --lines 100
personzit logs --service worker --follow
personzit logs --service dingtalk --follow
```

`--follow` 会持续输出新增日志并自动跟随跨天生成的新文件。

每条钉钉消息都会生成 `message_id`。钉钉日志按顺序输出：

1. `received`：消息已进入 Stream 入站链路，并带 `text` 原始消息摘要
2. `authorization`：白名单是否通过
3. `intent-precheck` / `intent-start` / `intent-finished`：固定规则是否命中、未命中后交给哪个自然语言 Provider、解析出的 action、置信度和耗时
4. `route-selected`：带原始消息、解析出的需求/路径/任务 ID、后续交给谁处理，以及执行模式
5. `local-inspection-start/finished` 或 `task-created`：本地查看或任务入队
6. `command-start` / `command-finished` 或本地查看阶段：具体执行器、模式和结果
7. `reply-start` / `reply-finished`：PersonZit 向钉钉 Stream 回写结果
8. `trace-summary`：一行汇总 `received -> authorized -> intent -> action -> executor -> mode -> reply`，并拆分意图解析耗时、执行耗时和总耗时；超过 3 秒会标记 `performance=slow`

Worker 日志会继续输出 `task route`：`planner-start/finished`、`workspace-prepared`、`agent-start/finished`、`verification-start/finished`。钉钉日志里的 `task-created` 带 `task_id`，可以用这个 ID 关联 Worker 日志。

示例：

```text
route message_id=abc123 {"stage":"route-selected","inbound":"dingtalk-stream","text":"你好","action":"chat","intent_provider":"bailian","intent_model":"qwen-plus","executor":"bailian","mode":"chat"}
route message_id=abc123 {"stage":"local-inspection-start","action":"inspect","executor":"codex","mode":"read-only","workspace":"D:\\Workspace"}
task route task_id=TASK-登录功能-000001 stage=agent-start {"subtask":"TASK-登录功能-000001-ST-001","executor":"codex","mode":"workspace-write","workspace":"D:\\Workspace\\PersonZit\\tasks\\TASK-登录功能-000001"}
```

API 日志包含每次 HTTP 请求的状态码和耗时；钉钉日志包含 Stream 心跳、入站原文、解析出的指令、最终回复内容和出站测试结果。`personzit dingtalk status` 会显示自然语言解析的有效 Provider/模型，以及 `DASHSCOPE_API_KEY` 或 `ZHIPU_API_KEY` 是否已加载。

## 5. 任务管理

### 5.1 创建任务

```powershell
node bin/personzit.js task create `
  --title "示例任务" `
  --description "实现并测试一个功能" `
  --project "$PWD"
```

返回的 JSON 中记下任务 ID。新任务 ID 会从问题中提取关键信息，而不是只使用递增编号，例如：

```text
TASK-前置事件融合处理失败-EventSubjectDOMapper-PXC-4518-000010
TASK-登录功能-000011
```

生成规则：

- 保留需求第一段中的业务问题摘要；
- 提取文件名、模块名、错误码等关键工程线索；
- 末尾保留短序号，仅用于防重和 trace 关联；
- 旧任务 `TASK-000001` 格式仍可查询、审批、取消，保证兼容。

钉钉创建任务采用“优先响应”流程：意图识别完成后立即回复已理解的需求和准备执行的动作；随后创建任务并入队规划。规划完成后：**需求明确则自动进入执行队列（不再等待人工审批）**，信息不足则推送澄清问题；完成、失败或等待人工处理时再次主动推送结果。CLI/API 创建的任务仍保留计划人工审批模式，便于本地高风险操作把关。

钉钉任务需求明确时，此处状态会快速经过 `QUEUED` 直接进入执行；只有 CLI/API 任务会停留在 `WAITING_FOR_APPROVAL`（等待人工审批）。在 `master` 分支或 `always-worktree` 策略下，任务目录、Worktree 分支、方案文档和 artifacts 也使用这个语义任务 ID，不再创建含义不明的 `TASK-000010` 目录。

### 5.2 查看任务列表与详情

```powershell
node bin/personzit.js task list
node bin/personzit.js task show TASK-000001
```

### 5.3 审批通过（CLI/API 任务）

```powershell
node bin/personzit.js task approve TASK-000001
```

审批后任务进入 `QUEUED`，Worker 默认每 1 秒轮询一次，会自动领取并执行。

> 钉钉群消息创建的任务不走此步骤：需求明确时规划完成即自动入队执行，信息不足时推送澄清问题。

### 5.4 确认执行完成

稍等 2~3 秒后再次查看：

```powershell
node bin/personzit.js task show TASK-000001
```

使用默认 MockAgent 时，状态应依次变为 `EXECUTING` → `VERIFYING`，最终为 `COMPLETED`。

### 5.5 查看事件与报告

```powershell
node bin/personzit.js task events TASK-000001
Invoke-RestMethod http://127.0.0.1:8765/api/tasks/TASK-000001/report
```

以上全部通过，即表示部署成功。

## 6. 日常使用指南

### 6.1 创建任务的两种方式

**方式一：完整字段创建**

```powershell
node bin/personzit.js task create `
  --title "任务标题" `
  --description "任务详细描述" `
  --project "D:\path\to\your\project" `
  --priority 10
```

- `--title`：必填，1~255 字符
- `--description`：必填
- `--project`：必填，任务关联的项目路径（建议使用绝对路径）
- `--priority`：可选，数字越大越优先被 Worker 执行，默认 0
- `--verify`：可选，自定义验收命令，**可重复传入**（如 `--verify "npm test" --verify "npm run build"`）；不传时按项目类型自动检测（Node 项目自动 `npm test`，Python 项目自动 `python -m pytest`）

**方式二：一句话需求**

```powershell
node bin/personzit.js run "给项目增加一个README" --project "D:\path\to\your\project"
```

（`--project` 默认为当前目录）

### 6.2 任务状态说明

| 状态 | 含义 |
|---|---|
| `NEW` | 新建 |
| `ANALYZING` | 需求分析中 |
| `WAITING_FOR_CLARIFICATION` | 等待澄清（用 `task clarify` 回答） |
| `PLAN_PROPOSED` | 计划已生成 |
| `WAITING_FOR_APPROVAL` | 等待人工审批 |
| `QUEUED` | 已入队待执行 |
| `EXECUTING` | 执行中 |
| `VERIFYING` | 验收中 |
| `REPAIRING` | 验收失败修复中 |
| `WAITING_FOR_HUMAN` | 等待人工介入 |
| `PAUSED` | 已暂停 |
| `CANCEL_REQUESTED` | 已请求取消 |
| `COMPLETED` / `CANCELLED` / `FAILED` | 终态 |

### 6.3 审批（CLI/API 任务；钉钉任务需求明确时自动执行）

```powershell
# 通过计划审批（进入执行队列）
node bin/personzit.js task approve TASK-000001

# 驳回（回到分析阶段重新规划），当前需通过 API：
Invoke-RestMethod -Method Post -Uri http://127.0.0.1:8765/api/tasks/TASK-000001/reject `
  -ContentType "application/json" -Body '{"reason":"计划需要调整"}'

# 查看审批记录
Invoke-RestMethod http://127.0.0.1:8765/api/tasks/TASK-000001/approvals
```

#### 高风险验收命令二次审批

如自定义验收命令包含 `push`、强制覆盖、删除、移动、改变远程仓库等高风险操作，Worker 不会直接执行，而是：

1. 任务从 `VERIFYING` 转为 `WAITING_FOR_HUMAN`
2. 创建一条 `type=VERIFICATION` 的审批记录，并记录 `HIGH_RISK_PENDING` 事件
3. 用户确认命令内容后执行同一个 approve 命令：

```powershell
node bin\personzit.js task events TASK-000001
node bin\personzit.js task approve TASK-000001
```

批准后任务回到 `VERIFYING` 并执行该命令；如需驳回，使用 `task reject`（或 API `POST /api/tasks/{id}/reject`）。CLI 的 `task approve` 同时支持计划审批和高风险验收审批，具体含义由当前待审批记录决定。

### 6.4 暂停 / 恢复 / 取消 / 重试

```powershell
node bin/personzit.js task pause  TASK-000001 --reason "先放一放"
node bin/personzit.js task resume TASK-000001
node bin/personzit.js task cancel TASK-000001 --reason "不需要了"
node bin/personzit.js task retry  TASK-000001
```

> 注意：`retry` 受状态机限制，仅适用于特定非终态场景；对 `COMPLETED` 等终态任务调用会返回“非法状态转换”错误。

`task runs` 展示每次 Agent 调用的状态、退出码、提示词、stdout/stderr 文件路径和结构化结果，便于审计与排障。

### 6.7 真实执行模式（P0 已实现）

Worker 按「子任务建议 Agent → 角色路由 → 配置默认」顺序选择可用 Agent：

| 角色 | 首选 | 备用 |
|---|---|---|
| implementation / test | codex | claude |
| requirement / design / review | claude | codex |

执行特性：

- **当前分支优先**：`workspace.isolation_policy: current-branch-except-master`（默认）时，Git 项目直接在当前分支执行，不创建额外目录；当前分支为 `master` 时才在 `workspace.tasks\<TASK-ID>` 创建 Git Worktree 和 `personzit/<task-id>` 分支
- **自动验收**：按计划中的验收命令在工作区内执行，通过才允许 `COMPLETED`
- **自动修复循环**：验收失败自动进入 `REPAIRING`，携带失败原因重新调用 Agent 修复（默认最多 2 次），仍失败则转 `WAITING_FOR_HUMAN`
- **Codex 沙箱**：`--sandbox workspace-write`，只能写工作区目录
- 如需恢复每个任务都隔离，可设置 `workspace.isolation_policy: always-worktree`；非 Git 项目仍回退到 `workspace.tasks\<TASK-ID>` 独立目录执行（事件中记录 `WORKSPACE_FALLBACK`）

### 6.8 AI 规划与澄清（P1 已实现）

在 `config.yaml` 中启用：

```yaml
planner:
  type: ai        # mock=固定模板；ai=调用 Claude/Codex 真实规划
  agent: claude   # 规划首选 Agent，不可用时自动回退 codex
  timeout_seconds: 300
```

特性：

- **异步规划**：创建任务后立即返回 `ANALYZING`，Worker 通过 `PLAN_TASK` Job 调用 AI 生成计划（不阻塞 API）
- **严格 JSON 计划**：自动解析/清洗模型输出，异常时回退 MockPlanner 并记录 `PLANNER_FALLBACK` 事件
- **多子任务依赖执行**：按 `dependencies` 拓扑排序调度，检测循环依赖
- **自动澄清**：AI 判断信息不足时进入 `WAITING_FOR_CLARIFICATION`，回答后自动重新规划：

```powershell
node bin\personzit.js task show TASK-000004   # 查看 clarification_questions
node bin\personzit.js task clarify TASK-000004 --answer "答复一" --answer "答复二"
```

- **驳回重规划**：`reject` 后自动重新生成计划

### 云端理解 + 本地 Agent 执行的混合模式（推荐）

PersonZit 的核心定位不是替代 Codex/Claude，而是作为钉钉到本机编程 Agent 的监管面。云端模型解决自然语言入口和非任务聊天，本机 Agent 解决工程规划与执行：

```text
钉钉消息
  -> PersonZit 鉴权 / 队列 / 留痕
  -> 云端模型识别自然语言意图，普通聊天直接回复
  -> 工程任务由本机 Codex 生成 JSON 计划
  -> 需求明确自动进入执行；信息不足则推送澄清问题并绑定后续补充上下文
  -> Codex / Claude 在项目当前分支执行子任务（master 自动改为 Worktree 隔离）
  -> PersonZit 汇报结果、产物、耗时和验证情况
```

推荐配置：

```yaml
planner:
  type: ai
  provider: local
  agent: codex

dingtalk:
  natural_language:
    enabled: true
    provider: zhipu    # 也可使用 bailian；Key 必须是普通按量计费 API Key
    model: "GLM-5.3-FlashX"
    max_tokens: 768
    temperature: 0

agents:
  default: codex
```

在该模式下：

1. 高置信度固定指令先由本地规则识别，保证管理命令稳定且低延迟。
2. 规则未覆盖的自然语言交给云端模型解析；普通聊天在同一次意图识别中直接生成自然回复。
3. 云端模型只输出结构化 intent JSON，不接收本地文件内容，也不直接执行本地操作。
4. 工程任务规划由本机 Codex/Claude 输出，PersonZit 只负责校验 JSON、落库、生成方案文档和排队。
5. 子任务执行时才进入授权工作区：Codex 使用 `workspace-write`，Claude 使用 `acceptEdits`。
6. 钉钉是指挥和感知入口，云端模型是语言理解面，PersonZit 是监管控制面，Codex/Claude 是真正的规划与执行引擎。
7. PersonZit 启动的是隐藏的 Codex/Claude 子进程，不附加到你手工打开的交互式 CLI；这样才能把进程绑定到任务、执行目录、采集日志并发送取消信号。默认直接使用项目当前分支，只有 `master` 才使用 Worktree。`GLM-5.3-FlashX + max_tokens=768` 是当前推荐的自然语言延迟配置。

### 手动 Codex / Claude 会话监管

PersonZit 的监管面不只覆盖自己创建的任务，也覆盖你日常手动打开的 CLI 会话：

1. **Codex**：Worker 每 5 秒增量扫描 `%USERPROFILE%\.codex\sessions\**\*.jsonl`，只识别 `originator=codex-tui` 的手动会话；读取 `task_started` / `task_complete` 事件并提取最终消息。
2. **Claude**：增量扫描 `%USERPROFILE%\.claude\projects\*\*.jsonl`，只识别 `entrypoint=cli` 的手动会话，排除 PersonZit 自己调用的 `sdk-cli` 会话；每轮用户指令和可见 assistant 输出都会进入监管状态。
3. 首次启用时会为已有会话建立基线，不重放历史消息；但**发现时仍在运行的任务会补发“开始”通知**，多个 Codex/Claude 窗口并发时不会漏报开始事件。之后的新任务开始、Claude 阶段输出、Codex 完成会通过钉钉 Webhook 主动推送。
4. 每个会话分配短 ID，例如 `EXT-CODEX-0001`、`EXT-CLAUDE-0002`。发送 `运行` 可查看当前手动会话、任务摘要和工作目录。
5. 发送 `指挥 EXT-CODEX-0001 修正登录超时并补充测试`：
   - Codex 使用原生 `codex queue --thread <session-id> --message <修订要求>`，把消息插入你当前打开的 TUI 原会话；
   - Claude 使用 `claude --resume <session-id> --print <修订要求>` 恢复原会话执行，并把结果返回到钉钉。
6. Claude 没有像 Codex 一样的显式本轮完成事件；当它会话产生可见阶段输出时先推送“手动会话输出”，后续背景任务继续产生输出时会再次推送。这是保守策略，避免把仍在后台调查的任务误报为最终完成。
7. 监控状态文件采用**原子写入 + 备份**（external-agent-monitor.json / .json.bak）：主文件被杀毒、备份软件或并发读取短暂锁住时自动回退备份；主备均不可读时跳过本轮扫描而不是重置状态，避免把进行中的任务误当历史基线吞掉通知。
7. 配置项位于 `external_monitor`：

```yaml
external_monitor:
  enabled: true
  interval_seconds: 5
  lookback_hours: 168
  list_hours: 24
  notify_started: true
  notify_claude_updates: true
  command_timeout_seconds: 1800
```

> 说明：PersonZit 不读取或推送 API Key，只解析本机 Codex/Claude 已落盘的会话 JSONL。若未来 CLI 日志格式变化，扫描会安全降级为记录 warning，不影响原 CLI 运行。


### 外部 Provider 配置

如果希望普通聊天和模糊意图解析更自然，可以配置智谱/百炼普通按量计费 API，只作为 `dingtalk.natural_language.provider`：

```yaml
ai_providers:
  zhipu:
    model: "your-glm-model"
  bailian:
    model: "your-qwen-model"

planner:
  type: ai
  provider: local
  agent: codex

dingtalk:
  natural_language:
    provider: zhipu
```

`百炼` 使用 `DASHSCOPE_API_KEY`；`智普` 使用 `ZHIPU_API_KEY`。API Key 只从环境变量/Windows 环境变量注册表读取，不写入配置。

> **不要把百炼 Coding Plan / Token Plan Key 或 Endpoint 用于 PersonZit 的直连 Provider。** PersonZit 的 `bailian` 配置面向普通百炼 OpenAI-Compatible API，默认地址是 `https://dashscope.aliyuncs.com/compatible-mode/v1`。百炼官方文档限制 Coding Plan / Token Plan 仅能在 AI 编程工具和 OpenClaw 类 Agent 中使用，不能用于自定义应用、自动化脚本或应用后端直接调用 API。因此 PersonZit 这种后端直连自然语言解析/规划接口应使用普通按量计费 API Key。Coding Plan 如需使用，应配置给本机 Codex/Claude 等编程工具自身，而不是配置为 PersonZit 的 `DASHSCOPE_API_KEY` 直连调用。

在 Windows 上修改用户级环境变量后，已经打开的 PowerShell 和由它派生的服务父进程不会自动刷新。PersonZit 启动时会做兜底：如果当前进程没有对应变量，会继续读取当前用户和机器级环境变量注册表。仍建议修改后重新打开 PowerShell，再执行 `restart`。

```powershell
$env:ZHIPU_API_KEY="your-key"
$env:DASHSCOPE_API_KEY="your-key"
node bin\personzit.js restart
Invoke-RestMethod http://127.0.0.1:8765/api/ai/providers
```

分层规则：

1. **PersonZit**：负责钉钉接入、鉴权、意图路由、任务状态、审批、日志、队列、执行目录策略和结果感知。默认当前分支执行，`master` 才 Worktree 隔离。
2. **Codex / Claude**：负责工程规划与本地执行。规划/意图解析使用只读模式；查看类任务使用 Codex `read-only`，Claude 备选 `plan`；工程修改类任务使用 Codex `workspace-write`，Claude 备选 `acceptEdits`。
3. **可选智谱/百炼普通 API**：仅用于提升模糊聊天和意图解析速度，不负责本地文件执行，也不是任务结果来源。
4. **默认授权工作区**：`D:\Workspace\PersonZit`。任务目录为 `tasks\TASK-xxxxxx`，需求/方案文档为 `documents\TASK-xxxxxx-plan.md`。启用 `authorize_agents` 后，Codex/Claude 会额外获得该根目录授权。
5. **本地查看白名单**：仅 `dingtalk.local_actions.allowed_roots` 中的路径可被 inspect，越界路径直接拒绝。

> 开通入站步骤：在[钉钉开放平台](https://open.dingtalk.com)创建/打开企业内部应用，添加机器人能力，将消息接收模式设为 **Stream 模式**，复制 AppKey/AppSecret 填入 `client_id/client_secret`，发布应用版本，并把该企业机器人添加到目标群。群自定义机器人的关键词只影响出站通知；推荐安全设置选择“加签”，如必须使用自定义关键词，建议关键词设为 `PersonZit`。

## 9. 已知限制（v0.1.0）

使用前请了解以下限制，避免误判为部署问题：

1. **取消未闭环**：`cancel` 仅将状态置为 `CANCEL_REQUESTED`，暂无组件将其推进到 `CANCELLED`。

3. **无鉴权**：API 未实现身份校验（`PERSONZIT_API_TOKEN` 仅由 CLI 附加请求头，服务端不校验）。

| 提示“服务不可用，请先运行 personzit start” | API 未启动或已退出 | 执行 `start`，并用 `logs --service api` 查看报错 |
| `init` 提示创建 Python 虚拟环境失败 | 未安装 Python 或版本低于 3.11 | 安装 Python ≥3.11 并确认 `python --version` 可用 |
| `init` 提示安装 Python 依赖失败 | 网络或 pip 源问题 | 检查网络，或为 pip 配置国内镜像后重试 |
| 审批后任务一直停在 `QUEUED` | Worker 未启动或已崩溃 | `node bin/personzit.js status` 检查，查看 `logs\worker.log`，必要时 `restart` |
| 端口 8765 被占用 | 其他程序占用端口 | `netstat -ano | findstr 8765` 定位进程后处理，或手动以其他方式启动服务并用 `PERSONZIT_API_URL` 指向 |
| `stop` 后残留进程 | PID 文件与实际进程不同步 | `node bin/personzit.js status` 查看 stalePid，手动结束对应进程 |
| 数据异常需要重置 | 测试数据污染 | `stop` 后删除数据目录中的 `data\personzit.db*`，再执行 `init` 重建 |
| 中文输出乱码 | PowerShell 编码问题 | 执行 `chcp 65001` 或 `[Console]::OutputEncoding=[Text.Encoding]::UTF8` |

### pip 镜像配置（国内网络必做）

若 `init` 时出现 `SSLEOFError` 或 `Could not find a version that satisfies the requirement setuptools`，说明 pip 直连 pypi.org 失败。执行以下命令切换为清华镜像，然后重新运行 `node bin/personzit.js init`：

`powershell
New-Item -ItemType Directory -Force -Path "$env:APPDATA\pip" | Out-Null
@'
[global]
index-url = https://pypi.tuna.tsinghua.edu.cn/simple
trusted-host = pypi.tuna.tsinghua.edu.cn
'@ | Set-Content -Path "$env:APPDATA\pip\pip.ini" -Encoding ASCII
`

验证镜像是否可用：

`powershell
python -m pip index versions setuptools
`

能列出版本号即配置成功。

### 数据备份

所有运行数据集中在数据目录（默认 `%USERPROFILE%\.personzit`）。备份时：

1. 先执行 `node bin/personzit.js stop`
2. 完整复制该目录（重点：`data\`、`config.yaml`）

### 卸载清理

```powershell
node bin/personzit.js stop
Remove-Item -Recurse -Force "$env:USERPROFILE\.personzit"
# 如做过 npm link，再执行：
npm unlink -g personzit
```

最后删除项目目录即可。
